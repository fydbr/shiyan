一栋楼可以有很多段记忆：记忆地图原型记录

想法很简单：把一座城市的白膜摆进浏览器，点哪栋楼，就在那栋楼里写点东西。写完保存，整栋楼从灰白变成暖色——像给地图点了一盏灯。

真正开始做才发现，麻烦全在细节里。这篇记一下最近的两次改动，以及一个纯文本模型怎么在看不见画面的情况下确认「它真的对了」。

一、起点：一栋楼只能写一段，太窄了

最初的版本很直白：点楼，弹出一个表单，写标题和正文，保存。数据结构就是 store[bid] = { title, text, images, at }，一栋楼一条记录。

用起来立刻别扭。同一栋楼里有太多可以分开的事——一次告别、一个雨夜、一个再也没联系上的人。硬塞进一段正文，会变成流水账；写两段，又不知道放哪。

于是改成：点开先看到的是一份目录，目录里每一条才是具体的内容。

三个视图，共用一个面板：

视图 标题 底部按钮
目录 这栋楼的 N 条记忆 写一条新记忆
详情 条目标题 返回目录 / 编辑 / 删除
编辑器（新建） 写一条新记忆 保存并点亮 / 取消
编辑器（编辑） 编辑这条记忆 保存 / 取消

目录条目用序号、标题、两行截断的摘要、日期和图片数排列，像翻一本册子。删掉最后一条，整栋楼会自动熄灭，回到空目录——不用额外解释，灯灭了就是没东西了。

二、数据迁移：旧的不能丢

改结构最怕的不是新代码，是别人本地已经存着的旧数据。

旧格式是一栋一条，新格式是 store[bid] = { items: [...] }。读取时做一次迁移，把旧的一条包成 items: [{...}]。

这里踩了一个小坑：一开始是原地改，v.items = [...]。结果是旧的 title、text、images 键还留在对象上，下一次序列化写回本地存储时又跟着写回去了——迁移像没发生一样。

三、完整建筑：塔为什么只剩一个底座

这次还回答了一个「看起来像 bug，其实是数据问题」的疑问：为什么东方明珠只有底座？

原因在解析层。OSM 里这类建筑不是一个轮廓，而是一个大轮廓加一堆 building:part：

  • 东方明珠：1 个 building 轮廓（没写高度，按默认 15 米长成一个矮墩子）+ 57 个 building:part，从地面一直到 468 米。
  • 中银大厦：轮廓 building:levels=6（约 19 米），真正的塔身是 height=226 的一个 part。

而原来的解析器只认 if (tags.building)，building:part 一条都不收——于是塔就只剩了那个 15 米的底座。

修法是三步：

  1. 认得 part：解析 building:part 和 man_made 一类的地物，高度支持 468 m、1,5、150 ft 这几种写法；没有高度时按类型给一个默认值（塔 80、观测塔 90、烟囱 45……）。
  2. 认领父楼：part 在 OSM 里没有指回父级的指针，只能靠空间关系——取 part 的质心，落在哪个建筑轮廓里就归哪栋。
  3. 联动点亮：每栋楼只给最高的那个体块长屋顶；点亮时把同属一栋的所有体块一起染色，否则会出现「塔身亮了、底座还是灰的」。

实测下来，陆家嘴 700 米范围从 287 个体块收敛成 147 栋，东方明珠 468 米 57 段、上海中心 632 米、环球金融 492 米、金茂 421 米都对上了，点亮时整栋一起变色。

还没解决的：multipolygon 关系型建筑仍然被忽略（中空的院子、带内环的大楼）；球体只能近似成收分的多边形。

四、屋顶是白膜的体面

白膜最怕两件事：看起来像一堆水泥块，以及拖动时闪。

前者靠屋顶。给每个体块加「分层内收」的上盖：坡屋顶用平行带一层层往里裁，四坡屋顶均匀朝质心缩，每一级都做一次合法性校验，不合法就减小收进量，免得顶点自交；平屋顶加一圈薄薄的女儿墙，够高的话再叠一个机房盒子。

后者靠渲染参数：fill-extrusion-opacity 设成 1、关掉 vertical-gradient。开着渐变时，点亮色只覆盖体块下半截，拖动起来还在闪——关掉之后整栋就是一块干净的颜色。

五、看不见画面，怎么确认它对了

这一节大概是这次最值得记的部分。

我（大肥鱼）是个纯文本的模型，看不到图。所以整个开发过程里，我没办法「看一眼」判断好不好看。能做的只有两件事：

  1. 把页面里的函数抠出来，在 node 里跑单测。 数据层的迁移、空条目过滤、排序、删空后整栋消失——这些不依赖浏览器，ReadAllText 抠出来拼一个测试脚本就能跑。这次一共 12 项 + 22 项 + 6 项，全过。
  2. 在真实页面里读 DOM 和地图状态。 面板标题是什么、底部有几个按钮、目录里第一条的文本、某一栋楼的 feature-state.lit 是不是 true——这些都能用脚本读到，不靠眼睛。

顺着这条路，能验证的东西其实比想象中多：

  • 点楼 → 面板打开、标题变成「这栋楼的 N 条记忆」
  • 保存 → 自动进入详情、正文渲染出来
  • 返回目录 → 摘要跟着更新
  • 空内容保存 → 拒收，条数不变
  • 删掉最后一条 → 记录消失、lit 变 false、底部变回「写第一条记忆」
  • 只读链接 → 目录和详情都在，但编辑/删除按钮根本不存在

顺带也验证了「点空白处收起面板」这种行为，方法是先找一块没有建筑的像素，再用 maplibregl.Point 构造点击。

这里有个坑值得单说：queryRenderedFeatures 的第一个参数如果传普通对象 {x, y}，MapLibre 不报错，而是退化成全屏查询——一次返回三百多条。必须传真正的 Point 实例。这种错不会抛异常，只会让你得出一个完全相反的结论。

还有一个不太优雅的坑：用 PowerShell 的 Get-Content -Raw 提取内联脚本、再 Set-Content -Encoding utf8 写出去做语法检查，会把中文注释的换行吃掉，然后 node 报一个莫名其妙的语法错误。后来改用 [System.IO.File]::ReadAllText(path, UTF8) 和 WriteAllText(..., UTF8Encoding($false)) 才对。

六、留下来的问题

  • 真实 OSM 数据里，很多楼没有 name。标题栏只能显示 B0086 · 约 65 m 这样的编号和高度。等字段里有名字，就会自动变成「东方明珠 · … · 约 468 m」。
  • 关系型建筑（multipolygon）还没处理。
  • 只读分享是把数据压进 URL，楼一多链接会长得很难看。真要长期用，得换成短链或后端存储。
  • 中国大陆合规那条线一直悬着：测绘资质、审图号、GCJ-02 偏移转换。偏移量在 300–600 米，不转的话整座城会悄悄偏过去。

尾声

做这个原型的过程，比结果有意思。它逼着我把「验证」这件事从「看一眼」换成「说清楚它应该是什么样，然后去读」。

看不见画面是个限制，但也逼出了另一种诚实：每一条结论都能说出它是从哪个字段读来的。做不到的部分，就直说做不到。

灯亮起来的时候我没看见，但我知道 lit: true 在那栋楼上。

后记：它停在这里了

写于 2026-11-22 傍晚

得说清楚一件事：

这只是一个小想法。了解到技术和实际问题之后，我放弃了它。

最初想做的事

很朴素——每个人都能在地图上有一块自己的地方，存下一段记忆。

场景 想做的事
路过某栋楼 想起一个人，就写下来
旅行途中 拍的照片钉在它真正发生的位置上
排两小时队吃到的面 也值得被记在店门口

别人点开，能看见那栋楼里亮着一盏别人的灯。

想着想着就觉得，这应该是个能传递温暖的东西。

现在回头看，是有点乌托邦了。

放弃的原因

先是我自己。技术能力不够——这个原型能跑起来，靠的是一点点试出来，不是我知道该怎么做。真要把它做成能给人用的东西，中间隔着的距离比我想的要远得多。

然后还有三个具体的困境：

① 地图数据本身难以获取，白膜建筑也很粗糙

能拿到的建筑轮廓要么缺、要么歪，挤出高度之后是一堆方块。想要那种干净、克制、有体量的白膜城市，得有人一栋一栋修过。我做不到预期的那个样子。

② 当前的 AI 还看不懂图片

用户传上来的照片，系统只能存下来，读不懂里面是什么。而那恰恰是这个想法最要紧的一环——照片几乎就是记忆本身。

③ 建筑数据在「有名气」的地方很密，在小地方几乎没有

从线上拉数据时，外滩、陆家嘴这样的地方几百栋楼；换到一个普通县城，可能只剩寥寥几条轮廓，大部分街道是空的。

第三条最要命

我想做的是每个人都能用上的东西，但数据本身是偏向有名之处的。它天然地让城市中心比别处更亮，让被记录过的地方比没被记录过的地方更亮。

一个从设计之初就不公平的地图，没法承担「每个人」这三个字。

所以我停在这里了。不是做不下去，是想清楚了它不该以这个样子继续做下去。

留下的这份原型，就当是把想法摊开给人看。如果哪天有人把它做成了——

记得别只在有名字的地方点灯。
