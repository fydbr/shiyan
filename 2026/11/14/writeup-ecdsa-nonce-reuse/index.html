两张盖过章的付款条 —— ECDSA nonce 重用伪造提款条

Flag：flag{x47_62c45a6f383e}

一句话：两条付款签名用了同一个 ECDSA nonce（r1 == r2），由此恢复私钥，再给空白的提款条补一个合法签名。

1. 题目与入口

平台开启了 TCP over WebSocket 代理：把 wss://…/api/proxy/<uuid> 用 wsrx connect 拉到本地端口，再 nc 127.0.0.1 <port> 即可。本质是一个一次性交互的密码学服务：连上后先吐一段 banner，然后只读一行输入，答对给 flag，答错回 no 并断开。

banner 长这样（每次连接都会重新生成密钥，所以数值每次都不同）：

字段 含义
curve / p,a,b,Gx,Gy,n secp256k1 全部参数，直接照抄即可
hash=sha256d 签名时对消息做 SHA256(SHA256(msg))，取 32 字节大端整数再 mod n
Qx,Qy 服务端公钥（私钥未知）
slip1/slip2 + r,s 两张已经盖过章（已签名）的付款条
withdraw 还空着、等待盖章的提款条

题目文案里的“章”就是 ECDSA 签名，“两张已经盖过章的付款条”就是两组 (r, s)。

4. 交互协议：只读一行

这是本题最容易卡住的地方——协议细节 banner 里没写。

实测结论：

  1. 服务端只读一行（readline 语义），读到换行才处理；只发数据不带 \n 会一直挂着。

  2. 提交格式是一行、空格分隔的两个 64 位十六进制数：

  3. 中间用 \t 分隔同样能过（解析器按空白切分）。

  4. 其他写法一律回 no 并断开，包括：r=…,s=…、r=…\ns=…、<r><s> 拼接、JSON、DER 编码、只交私钥/k 等。

判定“只读一行”的小技巧：先发 r=<合法 64 位 hex>\n 但不发 s。若服务端在等第二行，会超时无响应；若只读一行，会立刻回 no。本题是后者。再配合“不带换行则必超时”，就能确定协议是单行 readline。

另一个坑：每次连接都重新生成密钥，banner 里的 Q、r1、s1、s2 每次都不一样。所以“先连一次拿数据、算完再连一次提交”必然失败——恢复私钥、签名、提交必须在同一条连接内完成。

6. 时间线与踩坑记录

  1. 连上拿到 banner，r1 == r2 一眼看出 nonce 重用，公式三分钟推完。
  2. 卡在提交格式：先试 r=…\ns=…、r=…,s=…、拼接、JSON、DER，全部 no。
  3. 用“只发 r= 一行、不发 s”做对照实验，发现服务端只读一行，据此把搜索空间压到单行格式。
  4. 枚举分隔符时，"<r> <s>\n" 命中，返回 flag；再用 \t 分隔复现一次，确认解析器按空白切分。

7. 修复建议

  • 每次签名必须使用密码学安全随机、且互不复用的 nonce（RFC 6979 确定性 nonce 也可）。
  • 不要自己实现 ECDSA；用经过审计的库。
  • 服务端不要泄露同一密钥下的重复 r；若已泄露，应立即轮换密钥。
